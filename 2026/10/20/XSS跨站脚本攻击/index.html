XSS与SQL注入

比较维度 SQL 注入（服务端漏洞） XSS 跨站脚本攻击（客户端漏洞）
被欺骗的解释器 数据库 SQL 解释器（MySQL、PostgreSQL 等） 浏览器 HTML 渲染引擎与 JS 引擎（Blink、V8 等）
突破边界的常见字符 单引号 '、双引号 "、注释符 --、分号 ; 尖括号 < >、单双引号 ' "、斜杠 /、反斜杠 \
代码运行位置 后端数据库服务器 访问网页的终端用户浏览器
核心修复手段 参数化查询 / 预编译（Prepared Statements） 按语法位置做输出转义 + 安全操作 DOM + CSP
共同的根本成因 代码与数据未隔离：把不可信的用户输入直接拼接到了代码指令中

HTTP协议本身无状态

浏览器基础隔离机制：同源策略（SOP，Same-Origin Policy）

同源：两个URL的协议、域名、端口三个部分必须完全一样，才算同源

当前页面URL 目标访问URL 是否同源 原因说明
https://bank.com/user/info https://bank.com/user/pay 同源 协议、域名、端口完全相同
https://bank.com/user/info http://bank.com/user/info 不同源 协议不一
https://bank.com/user/info https://api.bank.com/info 不同源 域名不同
https://bank.com:443/info https://bank.com8080/info 不同源 端口不同

Set-cookie响应头的安全属性

属性名 示例值 作用说明 在xss的影响
Name=Value Session_id=abc123xyz Cookie的名称与实际内容 攻击者最常试图窃取的目标
Path Path=/ 指定该网站下那些路径的请求带上这个cookie。/代表全站所有路径 若现在在特定的子路径下，其他路径下的页面无法直接通过普通方式读取
Domain Domain=.example.com 指定cookie生效的域名范围 决定子域名直接是否共享这个cookie
Secure Secure 要求浏览器只在HTTPS加密连接下才发送该cookie 防止网络抓包窃听，但是拦不住页面内的JS脚本读取
HttpOnly HttpOnly 禁止页面内的JS通过document.cookie读取该cookie 重要的止损手段：能防止XSS脚本把cookie偷走，但不能阻止脚本在页面内直接发送请求
SameSite=Lax SameSite=Lax 控制从外站发起跨站请求时是否自动带上cookie（strict/Lax/none） 主要用来防止CSRF（跨站请求伪造），对本站页面执行的XSS没有防御功能

常见 Source
(可控输入源)		 location.search URL 中问号 ? 后面的查询参数。
location.hash URL 中井号 # 后面的锚点内容（默认只在浏览器本地使用，不发给服务器）。

document.referrer 跳转到当前页面之前的上一个页面地址。
window.name 当前浏览器窗口的名称，跨域跳转后依然保留，可被前序页面控制。
postMessage (event.data) 跨窗口通信接收到的消息内容。
常见 Sink
(危险执行点)		 element.innerHTML / outerHTML 把字符串当成 HTML 源码解析并插入页面（注意：直接通过 innerHTML 插入 <script> 不会执行，但插入 <img src=x onerror=...> 会执行）。
document.write() / writeln() 直接向文档流写入 HTML 字符串，写入的 <script> 和事件属性都会执行。
eval() / Function() 把传入的字符串直接当成 JavaScript 代码编译并运行。
setTimeout(str) / setInterval(str) 当第一个参数传的是字符串而不是函数时，效果等同于 eval()。
location.href = str 如果传入的字符串以 javascript: 开头，会直接作为代码执行。
